# SPEC.md — Taskbar Inn v0.3 設計の正本（抜本改訂）

タスクバー常駐の **incremental（インクリメンタル）宿経営ゲーム**。
実装はこの文書と `data/*.json` を真実とする。v0.2（方針 style 分岐）は**撤去**し、
本書のコンセプトに全面移行する。

---

## 0. コンセプトの中心（最重要）

idle/incremental ゲームの王道ループを宿経営で表現する：

```
①最前線の作業を手動でこなす（プレイヤースキルが伸びる）
  → ②稼ぎでスタッフを雇いその作業を自動化
  → ③手が空く
  → ④一段上のサービス階層が解放され、新しい作業が増える
  → ①へ（一層上で繰り返す）
```

**HITL（人間の操作）は常に「最前線」にあり、自動化が「過去」を食べる。**
ただ客が来て売上が出るだけにはしない。プレイヤーの仕事は
「最前線を手で回す → 自動化する → 次の階層へ上がる」こと。

深さの源泉は **プレステージ（暖簾分け）や支店拡張ではなく、一軒の宿を巨大化させること**
と、横方向のタスク種類の増加（Melvor Idle 式）。サービス階層は今後 **宿Lv** として扱い、
Lvが上がるほど同じ宿の中に作業・客・スタッフ職・メーター・設備部門が増える。

戦闘 idle の「エリアを選んで放置」に相当するのは **営業モード（§9）**。
展示による compulsion は **置き土産ドロップ＋陳列＋宿帳（§10）** で与える。

## 1. プレイヤースキルとアクティブ作業（Melvor 式）

- プレイヤーは同時に **1つの「作業モード」** を選択できる（未選択＝完全放置も可）。
- 選択中の作業は **クールダウン tick（既定 5 秒）ごとに 1 回実行** され、
  効果（メーターを下げる/在庫を上げる等）＋ そのスキルの **XP** を得る。
- スキル Lv が上がると **1 回あたりの効果が増える**（例：清掃 2 → 3 → 4 …は道具とスキルの合算で伸ばす）。
- スキル種別はサービス階層に対応して増える：
  - `cleaning`（清掃）… 階層① から
  - `hospitality`（もてなし）… 階層① から（現状は評判を小さく上げる暫定実装）
  - `cooking`（調理）… 階層② から
  - `harvesting`（収穫）… 階層② から（調理の上流素材を用意する）
  - `sourcing`（仕入れ）… 後続拡張
  - `engineering`（設備管理）… 階層④ から
- 作業モードはいつでも切替可。切替コストやスタミナは設けない（面倒回避）。
  「クールダウン式で少しずつ進む」ことで連打を不要にする。
- 作業対象が満たされている場合は自動で休憩に戻る。例：汚れ 0 の清掃、調理済み満タンの調理、
  野菜在庫満タンの収穫。

**手動作業の効果量（清掃の例）：**
```
manual_effect = base(=2) + player_skill_lv * per_level + player_tool_bonus
```
**手動作業の所要時間（設備効果）：**
清掃用具・厨房・畑などの基礎設備は、対応する手動作業のクールダウンを短縮する。
道具は1回あたりの効果量、設備は1回あたりの所要時間を伸ばす役割に分ける。
スタッフの自動クールダウンはこの設備短縮の対象外。

スキル定義は `data/skills.json`：
`id, name, icon, target("meter"|"stock"), affects(対象id),
base_effect, effect_per_level, cooldown_sec, xp_curve(base, growth)`。

## 2. スタッフ（自動化の担い手）＝ HITL の核

- スタッフは **選択中の作業と無関係に**、担当タスクをバックグラウンドで自動実行する
  （各自のクールダウンで毎 tick 評価）。
- **雇用は評判ゲート**：現在の reputation 帯によって、雇用候補に出るスタッフの
  **初期スキル Lv の上限** が決まる。評判が低いと低ステ人材しか雇えない。
- スタッフにも **スキル Lv** があり、稼働で XP を得て育つ。
  **雇用直後は 自動効率 < 手動**、育成すると **自動効率 > 手動** に逆転する
  → 序盤は手を出す理由、後半は放置する理由が自然に生まれる（active⇄idle 調律）。
- **配置枠に上限**（初期は 0 → チュートリアルで解放、以後 設備/階層で拡張）
  → 誰をどの作業に就けるかの**編成判断**。
- 雇用には一時金（gold）。日給などの継続費は階層②以降で導入を検討。
- **スタッフ管理の再設計候補**：現在実装は「職種＝担当スキル」がほぼ固定の簡易モデル。
  後続では「スタッフ個体にランダムパラメーター/適性を持たせ、雇用後に配置先を決める」方式を検討する。
  ただし頻繁な配置換えは宿経営の感触と合わないため、宿レベル・宿数・配置枠・部門数の増加に合わせて、
  どの規模まで管理させるかをゲームバランス上の要点として扱う。

**自動作業の効果量（清掃の例）：**
```
auto_effect = base + staff_skill_lv * per_level + staff_tool_bonus
```
スタッフ職定義は `data/staff_roles.json`：
`role_id, name, icon, skill(担当スキルid), base_auto_effect, effect_per_level,
cooldown_sec, hire_cost, cost_growth, reputation_req`。
個々のスタッフ実体（名前・現Lv・XP・配置）は game_state に保持する。

## 3. 道具（効率への投資・2系統）

掃除道具などツールは「効果量の下げ幅/上げ幅」への gold 投資どころ。バージョン（世代）制で
高度な道具ほど効果が大きい。**2系統に分ける**：

- **プレイヤー用ツール**：`player_tool_bonus` を上げる（手動効率↑）。
- **スタッフ用ツール**：`staff_tool_bonus` を上げる（自動効率↑）。
  **1個買えば全スタッフで共用**（人数分は不要）。

`data/tools.json`：`id, name, icon, skill(対象スキル), track("player"|"staff"),
tiers[{level,name,bonus,cost}]`。game_state に `tool_levels:{tool_id:level}` を保持。

## 4. upkeep メーター（階層ごとに増える）

throughput（客の回転）に応じて悪化し、作業で回復する**維持管理サブゲーム**。

| メーター | 悪化要因 | 回復手段 | 閾値超のペナルティ |
|---|---|---|---|
| `dirtiness`（汚れ） | 宿泊1回ごとに +d | 清掃（手動 or 清掃係） | 新規客減・評判− |
| `meal_stocks`（調理済みランク別在庫）※② | 食事提供で − | 調理（手動 or 料理人） | 食事提供不可→単価・客減 |
| `vegetable_stock`（野菜在庫）※② | 調理で消費 | 収穫（手動。農夫は後続） | 調理停止・食事供給低下 |
| `generic_ingredient_stock`（食材パック）※② | 調理の補助で消費 | dev/仮購入から開始 | basic〜good の詰み防止補助 |
| `ad_effect`（広告効果率）※③ | 時間で減衰 | キャンペーン/宣伝作業 | 集客率が基準へ低下 |
| 原料/生産ライン ※③④ | 加工で消費 | 収穫/生産（手動 or 農夫/技師） | 上位料理の供給停止 |

- **汚れの上限は宿の規模で増える**：素泊まり宿は `dirty_cap≈50`（すぐ汚れるが掃除範囲も狭く好バランス）。
  客室増設や階層アップで `dirty_cap` が上がり、**規模拡大すると手動だけでは回らず自動化必須**になる調整。
- 階層① では **汚れ 1 本に絞る**（メーター乱立を避ける）。②以降で順次追加。

## 5. 宿Lv（ランクアップの梯子）

旧称「サービス階層」は、今後は実質的に **宿Lv** として扱う。既存コードとの整合を優先し、
データファイル名と状態変数は当面 `service_tiers.json` / `service_rank` のまま運用する。

各Lvは同じ**階層テンプレート**を踏む：
「解放 → 新しい客ニーズ ＋ 新メーター ＋ 新スキル ＋ 新スタッフ職 → 手動で回す → 自動化 → 次へ」。

| 宿Lv | 名称 | 主なアンロック | 備考 |
|---|---|---|---|
| Lv1 | 小さな素泊まり宿 | 清掃、もてなし、汚れ、清掃係、客室/寝具/清掃用具 | 現在の基礎ループ。清掃と客の自動到着を完成形にする。 |
| Lv2 | 食事つき宿 | 調理スキル、収穫スキル、厨房、畑、食材保管庫、料理保管庫、野菜在庫 | 料理人はまだ解放しない。手動収穫→手動調理で食事提供を始める段階。 |
| Lv3 | 畑つき宿 / 自給の安定化 | 畑の本格拡張、野菜倉庫拡張、食材パック導線準備 | 収穫の初解放ではなく、自給体制を厚くし農夫/自動収穫へつなぐ段階。 |
| Lv4 | 取引宿 / 販路開拓 | 市場調査、商談、取引先、商人客 | 詳細実装は後続。今回は定義を先に置く。 |
| Lv5 | 名物宿 | 名物料理、果実、魚介/特産品、置き土産/宿帳強化 | 詳細実装は後続。収集と料理の接続点。 |
| Lv6 | 温泉宿 | 温泉採掘プロジェクト、温泉浴場、湯守り | 詳細実装は後続。大型プロジェクト型の解放。 |
| Lv7 | リゾート宿 | 醸造、VIP客、警備、庭園/酒場/用心棒詰所 | 詳細実装は後続。高単価・高リスク客の受け皿。 |
| Lv8 | 大規模ホテル | 部門長制、采配、設備管理、大型厨房/大型倉庫/管理事務所 | 詳細実装は後続。一宿巨大化の最上位。 |

相互依存（Melvor 式）：終盤は **畑 → 厨房 → 客** のチェーンが歯ごたえになる。
ランクアップ条件は実績ゲート（reputation / total_guests / 設備 Lv 等。gold 単独では上がらない）。
条件には `total_guests` / `reputation` / `skill.<id>` / `upgrade.<id>` / `action.<id>` を組み合わせる。
数値は仮で、最終調整は `docs/GAME_BALANCE.md` に寄せる。

階層定義は `data/service_tiers.json`：
`id, name, rank, unlock(条件), adds_skills[], adds_meters[], adds_staff_roles[],
adds_guest_needs[]`。

## 6. 設備ビルド（各階層の土台）

`data/upgrades.json`。カテゴリで役割を分ける（v0.2 の「全部 stat+1」を廃止）：

- **基礎**：客室🛏️(guest_capacity) / 寝具🛌(comfort) / 厨房🍲(food) / 清掃用具🧹(cleanliness)
- **内装投資**：暖炉🔥(comfort) / 調度品🪑(comfort) / 装飾🖼️(評判少)
- **特殊設備（実績アンロック）**：温泉♨️ / サウナ🧖 / 岩盤浴 / シアタールーム🎬 /
  ゲームセンター🎮 / 庭園🌷 / 酒場🍺 / 用心棒詰所🛡️ など
  - 解放前はグレーアウトで存在を見せる（目標提示）。解放後にレベル上げ可能。
  - 解放条件は gold で飛ばせない（reputation / total_guests / total_gold_earned / 基礎ステ）。
  - **個別アップグレードにするか、カテゴリ（例「館内施設」「アミューズメント」）でまとめた
    アプデ要素にするかは後続検討**（保留）。
- **撤去**：v0.2 の「厩舎(stable)」は削除。集客効果は広告/特殊設備へ移譲。

各要素：`id, name, icon, category, cost, cost_growth, effects{stat:delta},
unlock?(条件), max_level?`。

### 6.1 調理 / 倉庫 / 食材パックの方針

- 料理は Lv2 で「調理済みランク別在庫」へ拡張する。`meal_stocks:{rank:amount}` を正とし、
  旧 `food_stock` は互換フィールドとして合計調理済み在庫と同期する。
- 料理ランクは `basic`（簡単な食事）/ `standard`（家庭料理）/ `good`（宿の定食）/
  `luxury`（季節料理）/ `specialty`（名物料理）/ `vip`（特別会席）。
  現段階で実運用するのは `basic` / `standard` / `good` までで、`luxury` 以上はデータ上の予約枠。
- 調理作業は、厨房Lvと調理スキルLvから作れる最高ランクを決め、そのランクの調理済み在庫を増やす。
  仮ルールは「厨房Lv1=basic、Lv2=standard、Lv3+=good。ただし料理Lvが足りなければ一段下がる」。
- 客は `required_meal_rank` を持ち、要求ランク以上のうち一番低い在庫を消費する。
  なければ下位ランクの一番高い在庫を出し、評判の伸びを軽く下げる。完全に料理がなければ食事ボーナスなし。
- 倉庫は食材保管庫・料理保管庫・野菜倉庫・大型倉庫に分ける。現時点の `food_cap()` は互換維持用で、
  後続では各在庫カテゴリごとに cap を持つ。
- 食材パックは basic/standard/good までの不足補助として扱う。野菜、果実、魚介、肉、卵、調味料、特産品などを
  個別専用通貨にしすぎず、料理ランクや設備プロジェクトが参照できる素材カテゴリとして扱う。
- Lv2 初期実装では `harvesting`（収穫）で `vegetable_stock` を増やし、調理がそれを消費して
  `meal_stocks` を作る。`generic_ingredient_stock` は UI 上「食材パック」として basic/standard/good までの不足補助に使え、
  luxury 以上には原則使わない。
- Lv2 以降、野菜も食材パックも無い場合は調理作業を開始できない。自動の万能補充は入れず、
  まず収穫で素材を用意するループを成立させる。
- 本格実装までは、未接続の倉庫/特殊設備は `upgrades.json` に定義だけ置き、`effects:{}` で副作用を持たせない。

## 7. 客（自動で流れる）

到着・支払い・退室は**全自動**。プレイヤーは客を捌かない。
階層・営業モードで客種・ニーズが増える。マイナス要素は `security` で抑制する。

`data/guest_types.json`（階層/営業モードで解禁・ニーズで誘致）：
`id, name, icon, base_price_multiplier, tier_req, needs{stat/設備}, weight,
party_size?(複数人泊), drop_table?(置き土産), lines[], risk?`。

想定ラインナップ（段階解禁）：
一般人🧑 / 旅人🧳 / 旅商人💰 / 冒険者🗡️ / 経営者💼 / 宗教家🙏 / 政治家🎩 / 怪しい人🕵️ /
**インフルエンサー📱 / 有名人🌟 / 有名人のおしのび🕶️ / 家族👪（複数人泊）**。
- 怪しい人・政治家は高単価だがリスク。能動的な受入/拒否は**入れない**（incremental 向きでない）。
  security と設備で受動的に制御。
- **家族**：1 到着で `party_size` 分の capacity を消費し、人数分支払う。満室管理に厚みが出る。
- 有名人/おしのび/インフルエンサー：レア枠。評判ブースト＋レアドロップ源（§10）。

## 8. イベント（マイナス含む）

`data/events.json`：`id, type(positive|negative|guest), text, effects{}, cond?`。
security とメーター状態に応じて確率・被害が変わる。

マイナス例：無銭宿泊（怪しい人）／盗難（security低）／酔っ払いの喧嘩（酒場・冒険者過多）／
食中毒（food 低）／苦情・害虫（cleanliness低 or 汚れ高）／政治家スキャンダル（security低）。
→ `security` ステータスがここで主役の一つになる（v0.2 の「将来用」を解消）。

## 9. 営業モード（idle の「エリア選択」相当）

戦闘 idle の「エリアを選んで放置」を宿に翻訳した中核ピボット。プレイヤーは
**営業モード（今夜の狙い）** を1つ選んで放置し、モードが客プール・単価・リスク・
ドロップ表を変える（＝エリアごとの loot table）。

`data/business_modes.json`：
`id, name, icon, unlock?, guest_weight_mods{}, price_mult, risk_mult, drop_bonus{}`。

例：`通常営業 / 隊商の夜 / 祭り / 巡礼期 / VIPの夜（おしのび歓迎・高単価高リスク）`。
前回案の「広告キャンペーン」もここに統合（単発ブーストはモードの一時強化として扱う）。

**支店/立地拡張**（街道沿い・港町・城下町・温泉郷）は本作では保留。
v0.3 以降の本線は「複数の宿を並列管理する」より先に、**一軒の宿をLv8まで巨大化させる**
方向へ寄せる。営業モードは一宿内の客層・狙いを変える仕組みとして扱う。

## 10. ドロップと展示（compulsion）

- 客は退室時に低確率で **置き土産/忘れ物（ドロップ）** を残す。
  レアな客ほどレアな品（冒険者→戦利品/魔石、商人→珍品、政治家→書状、
  有名人→サイン色紙、おしのび→激レア）。ドロップ率は **営業モードの drop_bonus** で変動。
- **陳列棚**：集めた品を飾れ、**飾るとパッシブ効果**（戦利品→冒険者誘致＋、名士の色紙→評判＋）。
  展示が compulsion かつ実利になる。
- **宿帳（来客図鑑/bestiary）**：出会った客種を自動記録。レア客が埋めにくいエントリ＝コンプ目標。
  バッジ連動。
- 将来の専用ページ名は **「展示」**。置き土産・忘れ物・陳列・宿帳をまとめ、
  飾った品による集客、売上、評判へのパッシブ効果を扱う。

`data/collectibles.json`：`id, name, icon, source(客id/モード), rarity, display_effect{}`。
game_state に `collectibles_owned`, `collectibles_displayed`, `guestbook_seen` を保持。

## 11. 収入・評判ループ（自動）

毎 tick（1秒）評価。基本構造は v0.2 を継承しつつメーター・モードを噛ませる：

```
guest_rate  = f(rooms, reputation, 設備, ad_effect, business_mode) ; 汚れが高いと低下
on_arrival（capacity 未満・確率的）:
    type   = weighted_pick(guest_types)   # tier/needs/設備/モード バイアス
    n      = party_size                    # 家族は複数
    price  = (BASE + comfort*2 + food*2 + cleanliness) * type倍率 * モード倍率 * メーター補正
    gold  += price * n ; dirtiness += d * n ; （②: meal_stocks から必要ランクの料理を消費）
    低確率で drop 判定
reputation の伸び = f(cleanliness, food, 設備, 陳列効果) ; 汚れ高/食材切れ/マイナスで減衰
退室で guest_count を回転
```

**評判アンロック**：reputation が閾値に達すると、買える設備・雇える人材・営業モードが増える
（最初は適当でよい。`unlock` 条件に reputation を使う）。
正確さより「設備・スタッフ・階層・モードで体感が変わる」ことを優先。数値の正本は GAME_BALANCE.md。

## 12. オフライン進行 ＋ 再ログイン・ルーティン

- 終了/保存時に `last_saved_at` を記録。起動時に経過秒を **最大 28800 秒（8時間）** でクランプ。
- 留守中の収入・客を集計式で概算適用（ループせず軽く）。
- **留守中はメーターが悪化**：`dirtiness` 上昇（cap 近くで頭打ち＝青天井の放置収入を防ぐ）、
  `meal_stocks` 減少（②以降）、`vegetable_stock`/食材パック不足、`ad_effect` 減衰。
- **再ログイン時に「片付け」ルーティンが発生**：戻ったプレイヤーはまず清掃・補充に手を入れる。
  → セッション開始時に active、片付け後に idle へ、という自然なリズム。
- オフライン収入は「途中で汚れが溜まり客足が鈍る」前提で割り引く（インフレ防止）。
- 結果をトースト表示：滞在客 / 売上 / 評判 / 汚れ・在庫の現況 / イベント数。

## 13. チュートリアルとアンロックの流れ

序盤はチュートリアル駆動でアンロックを開放していく（手取り足取り→自走）：
- 開始：素泊まり宿・オーナー1人・配置枠 0・営業モードは通常のみ。
- 最初の客 → 汚れの発生と手動清掃を学ぶ。
- **5人宿泊 → スタッフ配置枠アンロック**（最初の雇用へ誘導）。
- 以後、評判/実績の節目で 道具・特殊設備・営業モード・サービス階層② が順次解放。

## 14. HITL と自動化の切り分け（要）

| | 自動化（面倒を消す） | HITL（楽しい負荷） |
|---|---|---|
| 実行 | 客の到着・支払い・退室／習熟スタッフの作業 | **最前線の新タスク（手動・クールダウン式）** |
| 配分 | — | **雇用・配置・育成（編成）／次に建て解放するもの** |
| ピボット | — | **営業モード選択／サービスのランクアップ** |
| 最適化 | — | **プレイヤースキル訓練／スタッフ育成／道具投資** |
| 収集 | ドロップ判定・宿帳記録 | **陳列の組み方（セットボーナス）** |
| 復帰 | オフライン収入の集計 | **再ログイン時の片付けルーティン** |

## 15. UI（compact / expanded）

- **compact（常駐小窓）**：眺めて分かる層。所持金・客の出入り・**メーター危険サイン**・
  現在の作業モードと進捗バー・客の吹き出し。手動作業が必要なときの合図（！）。
- **expanded（管理画面）**：HITL の本体。作業モード選択・雇用/配置/育成・道具・設備建設・
  ランクアップ・厨房状況・営業モード・展示/宿帳・実績。
- 現在の expanded は **左サイドバー + 右ページ** 構成。メニューは
  `ホーム / 仕事 / 厨房 / 設備 / スタッフ / 道具 / ログ / 実績`。
  - ホーム：定量ダッシュボード、通知、宿アップデート、資源の概要。
  - 仕事：作業カードとスキル詳細。
  - 厨房：宿Lv2以降の詳細ページ。調理済みランク別在庫、野菜/食材パック、現在作れる料理ランク、
    不足素材、客の要求料理ランク、調理ルールを確認する。調理操作そのものは仕事ページに残す。
  - 設備：設備投資一覧。
  - スタッフ：スタッフ詰め所または配置枠解放後に表示。スタッフ雇用とスタッフ一覧。
  - 道具：プレイヤー用/スタッフ用ツール投資。
- v0.3 では UI は「少しマシ」を目標（最低限のレイアウト整理・余白・読みやすさ・配色）。
  本格的なビジュアル磨きは後半フェーズ。

## 16. 開発用インフラ（dev/debug）

開発・バランス調整のために必須：
- **セーブリセット**（user://savegame.json 削除 → 初期状態で再起動）。
- **time scale**（×1 / ×10 / ×60）で時間経過を加速。
- **清算料金/ goldの倍率**ほかバランス値の調整。
- **デバッグオーバーレイ**（既定 F9 トグル）：gold/評判/メーター/スキルLv の直接編集、
  イベント強制発火、全アンロック、リセット。
- `data/dev_config.json`：`dev_mode:bool, time_scale, price_mult, ...`。
  起動時にこのフラグでデバッグ機能の有効/無効を切替（リリース時は dev_mode=false）。
